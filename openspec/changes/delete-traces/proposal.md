# delete-traces

## Why

trace 的生命周期管理缺了最后一环:**删除**。当前 trace 只能创建、标记完成/中止,永远堆积——真实使用场景里这是第一痛点:

- 调试过程产生大量一次性 trace(每次跑一遍就是一条),面板列表越长越难找目标;
- 导入错文件、Fork 实验做完,残留数据只能靠手删数据库文件;
- 本项目的存储是本地单文件,没有外置 GC,不提供删除就意味着"只进不出"。

用户在面板里已经自然地想找这个按钮(演示阶段面板里堆了多条旧演示 trace)。范围克制:单条删除 + 级联清理 + 面板删除入口(带确认);不做批量清理、不做回收站。

## What Changes

- **后端(store)**:`delete_trace(trace_id)` 级联删除该 trace 的决策点、上下文快照 diff、分支与 trace 本行;blob(内容寻址去重存储)保持不动(跨 trace 共享,孤儿块无行为影响)。
- **API**:`DELETE /api/traces/{trace_id}` → 200 `{"ok": true}`;不存在 404。
- **UI**:trace 列表项悬停显示「删除」入口,点击后确认框("将删除该 trace 及其全部分支与决策点")→ 调用删除 → 刷新列表;若删除的是当前选中的 trace,回到空选择态。
- **spec**:`recording` 能力新增「trace 删除管理」requirement(删除语义 + 面板入口)。
- **测试**:store 级联删除单测(含 fork 分支/上下文 diff 一并清除、其它 trace 不受影响)、DELETE API e2e(删除后列表/详情/决策点全部 404、其余 trace 完好)。

## Out of scope

- 批量删除 / 清空全部 / 回收站恢复;blob 的引用计数 GC(孤儿块无行为影响,推迟);多 trace 联合选择操作。

## Criteria

- 删除后:该 trace 从列表消失,详情/分支/决策点查询 404 或为空;同库其它 trace 及其分支决策点完好;fork 出的分支随父 trace 一并删除。
- 面板列表每条 trace 可删除(带确认文案);删除当前选中 trace 后回到空选择态。
- 全量测试通过,零回归。
